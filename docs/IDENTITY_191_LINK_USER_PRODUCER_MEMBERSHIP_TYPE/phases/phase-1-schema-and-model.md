# Phase 1 — Schema and Model Upgrade

**Issue:** #191 (`owner` / `manager` / `contributor` producer memberships)
**Status:** Complete
**Scope:** `wine_words_api` only

## Goal

Give every `producer_memberships` row exactly one typed role, with the database and the model agreeing on the three allowed values and nothing else.

## Files changed

| File | Change |
|---|---|
| `db/migrate/20261024000000_add_membership_type_to_producer_memberships.rb` | New forward migration (the original `20261021234637_create_producer_memberships.rb` is already applied everywhere and was **not** edited). |
| `app/models/producer_membership.rb` | Types, validation, scopes, helpers. |
| `spec/models/producer_membership_spec.rb` | Rewritten model spec (13 examples). |
| `db/schema.rb` | Regenerated by `db:migrate`. |

## Schema

```ruby
t.string "membership_type", null: false
t.check_constraint "membership_type::text = ANY (ARRAY['owner'::character varying, 'manager'::character varying, 'contributor'::character varying]::text[])",
                   name: "chk_membership_type"
```

The unique index `(user_id, producer_id)` from the original migration is unchanged, so "one membership per user/producer pair" is enforced twice (model + index).

### Migration is deliberately three-step

1. Add `membership_type` as **nullable**.
2. Count rows where it is still `NULL`. If any exist, the migration aborts with an actionable message and **rolls back** (Postgres DDL is transactional), so no half-typed table is left behind.
3. Enforce `NOT NULL` and the three-value check constraint.

Issue #191 forbids silently granting owner/manager access, so legacy rows are never mapped automatically. The operator states the approved mapping explicitly:

```bash
PRODUCER_MEMBERSHIP_LEGACY_TYPE=manager     bin/rails db:migrate  # preserves old edit access
PRODUCER_MEMBERSHIP_LEGACY_TYPE=contributor bin/rails db:migrate  # conservative / read-only
```

The value is whitelisted, interpolated through `quote`, and applied only to `NULL` rows. `manager` is the documented mapping because pre-#191 memberships already had full producer-edit rights.

`down` removes the constraint and the column. Because untyped rows cannot be represented once the column is dropped, rolling back loses the type — acceptable for a forward-only feature, and documented in Phase 8.

## Model

```ruby
MEMBERSHIP_TYPES = %w[owner manager contributor].freeze
EDITABLE_TYPES   = %w[owner manager].freeze
```

- `validates :membership_type, presence: true`
- `validates :membership_type, inclusion: { in: MEMBERSHIP_TYPES, allow_blank: true, message: "must be owner, manager, or contributor" }`
- `validates :user_id, uniqueness: { scope: :producer_id, message: "is already linked to this producer" }`
- Scopes: `owners`, `managers`, `contributors`
- Predicates: `owner?`, `manager?`, `contributor?`, `can_edit_producer?`

`follower` and `viewer` are rejected by the model **and** by the database constraint; there is no follow relationship in this release.

## Verification

```
bin/rails db:rollback STEP=1      # down removes constraint + column
bin/rails db:migrate             # up on 0 rows
PRODUCER_MEMBERSHIP_LEGACY_TYPE=manager bin/rails db:migrate   # exercised on 1 synthetic untyped row
bundle exec rspec spec/models/producer_membership_spec.rb       # 13 examples, 0 failures
```

The guard was exercised by leaving a real untyped row in the development database: the migration aborted with the inventory message, then succeeded and backfilled it as `manager`.

## Assumptions / deviations

- No column default. Writers must supply a type; the API does too (Phase 3).
- Staging/production membership row counts were not readable from this environment. If those environments hold rows, the migration will stop with the message above until an approved mapping is supplied — this is the intended safe failure.
- `membership_type` is a plain string with a check constraint rather than a Postgres enum, so adding a fourth type later is a normal migration, not an enum rewrite.
